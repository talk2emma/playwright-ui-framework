Utilities (src/utils)

src/utils/a11y.utils.ts

111 lines · 1 exports

Runs axe-core against a page or a subtree, attaches both a JSON and an HTML report to the test result, formats violations into a readable failure message, and fails the test by default when violations are found.

When you need to change it

  • You change the WCAG level you hold yourself to, need to exclude a third-party region, or want a different report format.

How to change it

  1. Change DEFAULT_WCAG_TAGS to raise or lower the bar for the whole suite.

    export const DEFAULT_WCAG_TAGS: WcagTag[] = ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'];

  2. Disable a rule only with a linked ticket and a date, so the exception is temporary by construction.

Why the change belongs here

failOnViolation defaults to true on purpose: accessibility regressions should break the build, not accumulate in a report nobody opens.

src/utils/browser.utils.ts

42 lines · 3 exports

Console capture: captureConsole records console errors, uncaught exceptions and failed requests into a container the consoleErrors fixture owns, so a test can assert the page logged nothing unexpected.

When you need to change it

  • You need to record another signal from the page — a specific console channel, a resource-timing entry.

How to change it

  1. Add the helper here and import it directly where it is needed. If every test needs it, promote it to a fixture instead.

Why the change belongs here

A page that throws in the console is usually broken even when the assertions pass. Capturing into a container the fixture owns means the check costs a test nothing to opt into.

Watch out for

  • captureConsole(page, into) records into an existing container — that is how the consoleErrors fixture avoids depending on page.

src/utils/data.utils.ts

54 lines · 3 exports

Seeded, reproducible test data. seedFaker makes a run repeatable from the test title, and generateUser builds a complete person. Generate rather than hard-code: a suite whose fixtures say alice@example.com fails the second time it runs against a uniqueness constraint.

When you need to change it

  • Your domain needs generators (an account number with a checksum, a valid VAT id), or you find a new input that breaks things.

How to change it

  1. Add the generator here so every test uses the same valid shape.

    export function generateIban(country = 'GB'): string {
  return `${country}${faker.string.numeric(2)}${faker.string.alpha({ length: 4, casing: 'upper' })}${faker.string.numeric(14)}`;
}

Why the change belongs here

Generated data with unique markers is what lets parallel workers run the same test without colliding on a shared record — the most common cause of "passes alone, fails in parallel".

Watch out for

  • The testData fixture seeds faker from the test title, so within a test the sequence is deterministic and reproducible on retry.

src/utils/date.utils.ts

58 lines · 3 exports

toIsoDate and format for writing dates into inputs and comparing them, and humanizeDuration for readable log and report output.

When you need to change it

  • You need a token the formatter does not support, or timezone-aware handling.

How to change it

  1. Add the token to the replacement map and to the regular expression in format. For timezone-sensitive assertions, freeze the clock with Playwright's own clock API instead of computing offsets.

    await page.clock.setFixedTime(new Date('2026-01-15T09:00:00Z'));

Why the change belongs here

Tests that compute "today" against a live clock fail at midnight and on daylight-saving boundaries. Freezing the page clock makes date-dependent UI deterministic.

src/utils/logger.ts

138 lines · 3 exports

Structured logging with console and file output, deliberately dependency-free. Five levels (error, warn, info, debug, trace), nested scopes, colour when attached to a terminal, and JSON-lines files at test-results/logs/test-run.log and errors.log.

Note
Errors and warnings go to stderr; everything else to stdout, so CI error streams stay signal-only.

When you need to change it

  • You need a new destination (a log aggregator), a different format, or an extra field on every line.

How to change it

  1. Add a sink and write to it in emit. Keep every write inside a guard — logging must never be the reason a test fails.

    class HttpSink {
  write(line: string): void {
    void fetch(process.env.LOG_ENDPOINT!, { method: 'POST', body: line }).catch(() => undefined);
  }
}

Why the change belongs here

General-purpose logging libraries pull in stream polyfills that break across Node releases; a test framework cannot afford a logger that fails to load. Everything needed here is a few dozen lines.

Watch out for

  • Workers are separate processes, so log lines from parallel tests interleave. The pid field on every record is how you separate them.

src/utils/network.utils.ts

155 lines · 1 exports

The network control surface for a page or context: mock a response, modifyResponse to rewrite a real one, abort to simulate failure, delay to exercise loading states, block heavy assets or third-party trackers, capture and search requests, wait for a specific response, and toggle offline.

When you need to change it

  • You need a new interception pattern — conditional mocking, recording to a fixture file, replaying a HAR.

How to change it

  1. Add the method to the class so it is available through the network fixture everywhere.

    async mockOnce<T>(pattern: string | RegExp, response: MockResponse<T>): Promise<void> {
  await this.target.route(pattern, async (route) => {
    await route.fulfill({ status: response.status ?? 200, body: JSON.stringify(response.body) });
    await this.target.unroute(pattern);
  });
}

Why the change belongs here

Error states, slow responses and third-party outages are extremely hard to reproduce against a real backend and trivial to reproduce here — which is what makes those paths testable at all.

Watch out for

  • The network fixture resets routes after each test, so a mock cannot leak into the next one.
  • Blocking third parties speeds runs and removes a large source of flakiness, but do not block them in tests whose purpose is the integration.

Related: src/fixtures/base.fixture.ts · src/types/index.ts

src/utils/retry.utils.ts

22 lines · 1 exports

waitUntil — polls a condition until it holds or the timeout elapses, and fails with a message naming the condition. Used where Playwright has no web-first assertion to wait on, such as a progress bar reaching a value.

Careful
These are for genuinely flaky boundaries — a third-party widget, a download that occasionally 502s. They are not a substitute for a web-first assertion; prefer Playwright’s auto-waiting and expect.poll first.

When you need to change it

  • You need a different backoff strategy, jitter, or a shared default policy.

How to change it

  1. Extend RetryPolicy in src/types/index.ts and honour the new field in retry.

Why the change belongs here

A retry that wraps every failure hides real bugs; retryOn is what keeps retrying honest by failing fast on errors that will never succeed.

src/utils/string.utils.ts

5 lines · 1 exports

normalizeText — collapses the whitespace the DOM inserts, so an assertion compares the text a person sees rather than the text the markup happens to contain. It is the single most-used helper in the framework: every component that reads text routes through it.

When you need to change it

  • Your application formats values in a way the parsers do not handle — a different decimal separator, a suffix like "1.2k".

How to change it

  1. Extend the parser here rather than in the assertion, so every test parses the same way.

    export function parseCompactNumber(value: string): number {
  const match = /^([\d.]+)([km])$/i.exec(normalizeText(value));
  if (!match) return Number(normalizeText(value).replace(/[^\d.-]/g, ''));
  return Number(match[1]) * (match[2].toLowerCase() === 'k' ? 1_000 : 1_000_000);
}

Why the change belongs here

Rendered text carries non-breaking spaces, line breaks and indentation. Normalising once removes an entire class of confusing string-comparison failures.

Reporters (src/reporters)

src/reporters/summary.reporter.ts

152 lines · 1 exports

A custom Playwright reporter that prints a compact end-of-run summary and writes reports/summary.json containing totals, every failure with its first error line, flaky tests, the five slowest tests and the full test list with tags and durations.

Expected failures are passes

A test annotated test.fail() is expected to fail, and Playwright records that in test.expectedStatus. Its raw result.status is still failed, so counting that directly reports a green run as red — which is exactly what happened once the suite began recording known defects this way.

The stored status is therefore the *outcome*: whether the result matched what was expected. An expected failure is a pass; an unexpectedly passing test.fail() is a failure — which is the whole point of the annotation, because it means the defect has been fixed and the annotation should be removed.

Note
expectedFailure is recorded per test, so a pipeline can report "111 passed, 4 of them documented defects" rather than hiding the distinction.

When you need to change it

  • A dashboard, Slack notification or PR comment needs another field — ownership, suite name, retry count, browser.

How to change it

  1. Add the field in onTestEnd where the test result is available, then include it in the summary object in onEnd.

    this.tests.push({
  // ...
  annotations: test.annotations.map((a) => a.type),
  browser: test.parent.project()?.use.browserName ?? 'unknown',
});

Why the change belongs here

CI needs machine-readable results. Answering "what broke and how slow are we" from a JSON file is far cheaper than downloading and unzipping an HTML report.

Watch out for

  • Passing --reporter=... on the command line replaces the configured reporters, so this one does not run on those invocations.

Test data (src/data)

src/data/personas.ts

144 lines · 6 exports

The seven SecureBank accounts and the facts about the seeded dataset that tests assert against.

Why credentials are in the repository

The framework's rule is that credentials never enter version control, and it is not being bent here. These are published on the application's own login page, in a table headed "Test credentials", for anyone to read. They authenticate nothing and protect nothing.

Treating them as secrets would mean handing every developer a .env before they could run a single test against a public practice app — ceremony with no security benefit. getUser() in env.config.ts remains the only route for credentials in every other environment.

The personas are the point

PersonaBehaviourWhat it makes testable
standardFull accessEvery happy path
lockedSign-in refused as suspendedA distinct message from a wrong password
frozenSigns in; money movement disabledTransfer, send and bill-pay all blocked
overdraftNegative balanceThe overdraft indicator
slowSlow loadingReal loading states
buggy (error_user)A planted defect in the loan totalProving the suite can find a bug
adminAdditional viewRole-dependent chrome

Negative paths and degraded states are reachable by logging in as somebody else, rather than by mocking a failure and hoping the mock resembles reality. That is unusual and worth exploiting.

SEED — dataset facts, read from the running app

Note
Every value in SEED was read from the application, not from its documentation. One of them was originally wrong: totalTransactions was recorded as 20 from a session that had already performed a transfer — each completed transfer adds a debit and a matching credit. The true figure in a fresh context is 18. Seed values must be read from a clean context, or they encode whatever the person exploring happened to do first.

When you need to change it

  • The application reseeds.
  • A persona is added or changes behaviour.

How to change it

  1. Update the constant. Nine specs read from SEED, so one edit covers all of them.

  2. Run the fixture-integrity test, which reads the app's own credentials table and compares it with this file.

    npx playwright test -g "personas fixture matches"

Why the change belongs here

A hand-written copy of a table the application renders itself will drift. Keeping the copy in one file, and testing it against the source, is what stops that drift being silent.

Watch out for

  • Read seed values from a fresh browser context. State lives in localStorage, so an exploratory session pollutes them.
