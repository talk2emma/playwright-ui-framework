Task-oriented runbooks. Each answers the same three questions: where to go, what to do, and why the change belongs there rather than somewhere else.

1. Point the framework at a real application

  1. Where: src/config/environments.ts. Set the real URLs for each environment.

    dev: {
  name: 'dev',
  baseURL: 'https://dev.yourapp.com',
  apiBaseURL: 'https://dev.yourapp.com/api',
  retries: 1,
  workers: undefined,
  ignoreHTTPSErrors: true,
},

  2. Where: .env. Set TEST_ENV and the credentials for each role.

    TEST_ENV=dev
STANDARD_USER=qa.standard@yourapp.com
STANDARD_PASSWORD=...

  3. Where: src/hooks/auth.setup.ts. Replace the placeholder selectors in signIn with your login page’s. This is the only file in the framework that must know your markup.

  4. Verify: run the setup project alone before anything else.

    npx playwright test --project=setup

Why here: URLs are non-secret configuration and belong in version control; credentials are secrets and belong in the environment; the login flow is application-specific and is deliberately isolated to one function so nothing else in the framework depends on your markup.

2. Add a page object for a new screen

  1. Where: copy src/pages/template.page.ts to src/pages/<feature>.page.ts.

  2. What: set path and readyIndicator, declare components as readonly fields, and write business actions.

    export class InvoicesPage extends BasePage {
  protected readonly path = '/invoices';
  protected readonly readyIndicator: SelectorLike = '[data-testid="invoices-root"]';

  private readonly factory = ui(this.page);
  readonly grid   = this.factory.dataGrid('[data-testid="invoice-grid"]', { name: 'Invoices' });
  readonly search = this.factory.input('[data-testid="search"]', { name: 'Search' });

  async searchFor(term: string): Promise<void> {
    await this.search.typeAndSettle(term);
    await this.grid.waitForData();
  }
}

  3. Where: export it from src/pages/index.ts.

Why here: the ready indicator is what makes navigation deterministic; declaring components as fields means a selector change is one line and editor autocomplete lists the whole page surface.

3. The component library does not cover my widget

  1. First: check whether an existing component only needs configuration. Most do — Dropdown, DataGrid, DatePicker, Autocomplete and the rest take their selectors as options.

    ui.dropdown('#country', { panelSelector: '.MuiAutocomplete-popper', optionSelector: '.MuiAutocomplete-option' });

  2. Then: if the behaviour differs, subclass and override only the method that differs.

    class HoverDropdown extends Dropdown {
  override async open(): Promise<void> { /* hover instead of click */ }
}

  3. Otherwise: create a new component under the right group in src/components/, extending BaseComponent.

    export class Timeline extends BaseComponent {
  protected override get componentType(): string { return 'Timeline'; }

  async getEvents(): Promise<string[]> {
    return this.step('read events', async () => {
      return (await this.locator.locator('.event').allInnerTexts()).map((t) => t.trim());
    });
  }
}

  4. Then: export it from src/components/index.ts and add a factory method in component.factory.ts.

  5. Finally: document it — add an entry to the matching module in scripts/docs/content/ and run npm run docs.

Why here: a widget behaviour written in a page object is invisible to every other page. Written as a component, it is available everywhere, reports itself in traces, and inherits all the base behaviour for free.

4. A test is flaky

  1. Diagnose first. Open the trace from the HTML report; the failing step is named after the component and action.

    npm run report

  2. If the wait is wrong: fix it in the component, not the test. Add a condition-based wait rather than a delay.

  3. If the timeout is genuinely too short: raise the named budget in src/config/timeouts.ts — never hard-code a number at the call site.

  4. If the data collides: use uniqueId() or the testData fixture so parallel workers cannot share a record.

  5. If a third party is unreliable: stub it with the network fixture, or block it.

    await network.mock('**/api/recommendations', { body: [] });
await network.blockThirdParty();

  6. If the app is genuinely slow: that is a product finding. Record it rather than hiding it behind a longer timeout.

Why here: a wait added to a test fixes one test; a wait added to the component fixes every current and future use of that element. Retries in playwright.config.ts mask flakiness — they are a safety net, not a fix.

5. Add a new environment

  1. Where: src/types/index.ts — add the name to EnvironmentName. TypeScript will now point at everything that must be updated.

  2. Where: src/config/environments.ts — add the entry with URLs, retries, workers and TLS policy.

  3. Where: src/config/env.config.ts — add the value to the TEST_ENV enum in the schema.

  4. Where: .github/workflows/playwright.yml — add it to the workflow_dispatch choice list.

  5. Verify:

    TEST_ENV=preprod npm run test:smoke

Why here: the union type is the mechanism that turns "add an environment" from a search-and-hope exercise into a compiler-guided checklist.

6. Add a configuration variable

  1. Where: src/config/env.config.ts — add it to the zod schema with a fallback.

    MAX_UPLOAD_MB: numeric(25),

  2. What: expose it on the exported config object in the shape callers should see.

    maxUploadMb: raw.MAX_UPLOAD_MB,

  3. Where: .env.example — document it with a safe placeholder.

  4. Where: the CI workflow, if it must be set there.

Why here: reading process.env at the point of use reintroduces exactly the failure mode this file exists to prevent — an unparsed string, a missing value, a suite silently pointed at the wrong host.

7. Add a browser, device or specialised suite

  1. Where: playwright.config.ts, the projects array. Copy an existing entry.

    {
  name: 'galaxy-s23',
  use: { ...devices['Galaxy S9+'] },
  dependencies: ['setup'],
  testIgnore: ['**/visual/**', '**/a11y/**'],
},

  2. Where: .github/workflows/playwright.yml — add it to the matrix if it should run in CI.

  3. Where: package.json — add a script if people will run it directly.

Why here: dependencies: ['setup'] is what gives the new project authenticated sessions; without it its tests start signed out and fail in a way that looks like an application bug.

8. Seed test data instead of clicking through the UI

  1. Where: src/api/endpoints.ts — add the route.

  2. Where: the test, or a fixture if several tests need it. A fixture also gives you automatic cleanup.

    order: async ({ api }, use) => {
  const order = await api.post<Order>(ENDPOINTS.orders.create, { items: [{ sku: 'A1', qty: 1 }] });
  await use(order);
  await api.delete(ENDPOINTS.orders.byId(order.id));
},

Why here: seeding over HTTP takes about 200 ms; the same setup through the UI takes 20 seconds and couples the test to screens it is not testing. When those screens break, the wrong test fails.

9. Add an assertion the whole team will reuse

  1. Where: src/fixtures/custom-matchers.ts.

  2. What: return pass plus a message function covering both directions — the negated message is what makes a matcher pleasant to debug.

  3. Alternative: if the assertion is about one element type, put it on that component as expectSomething() instead.

Why here: a named matcher produces a failure message that is diagnosable from a CI log alone, which expect(true).toBe(false) never is.

10. Change the reporting outputs

  1. Where: playwright.config.ts — the reporters array, for adding or removing a reporter.

  2. Where: src/reporters/summary.reporter.ts — to add a field to reports/summary.json that a dashboard or PR comment needs.

  3. Where: .github/workflows/playwright.yml — to change what is uploaded or retained.

Why here: summary.json is the machine-readable contract with CI. Extending it there keeps every consumer working; parsing the HTML report instead would break on the next Playwright upgrade.

11. Update visual baselines

  1. Confirm the change is intended. Open the diff images in the HTML report first.

  2. Regenerate, ideally in the container so the images match CI.

    npm run test:visual:update
# or: docker compose run --rm ui-tests --project=visual --update-snapshots

  3. Review the images in the pull request exactly as you would review code.

Why here: baselines are OS- and browser-specific. Regenerating on a laptop and running in CI produces diffs on every run, which is why the container exists.

12. Handle an iframe, a shadow root or a new tab

Why here: treating a frame as a scope rather than a component is what keeps iframe support out of all 37 component classes.

13. Onboard a new engineer

  1. Read Overview and Architecture here (about twenty minutes).
  2. Run npm ci && npx playwright install --with-deps, then npm run test:ui.
  3. Read src/core/base.component.ts — it explains more about the framework than any other file.
  4. Copy src/pages/template.page.ts and build a page object for one screen.
  5. Write one @smoke test using only page-object methods.
  6. Read Conventions before opening the pull request.
